## CAN 收不到数据 —— 双重根因（均已修复）

### 根因 #2（08:58 确诊）：MCAN 报文 RAM 未注册 → mcan_init 返回 2
- 诊断数据：`g_can_src_clk_khz=40000`（PLL1 修复已生效，时钟链路 OK），但 `g_can_init_stat=2`（status_invalid_argument）。
- 根因：HPM5361 的 `MCAN_SOC_MSG_BUF_IN_AHB_RAM=1`，MCAN Message RAM 在 AHB RAM(0xF0400000,32KB)，
  应用必须先调 `mcan_set_msg_buf_attr()` 注册，否则 `mcan_get_ram_size()=0` → mcan_init 返回 2（hpm_mcan_drv.c ~L1897）。
- 修复：can_app.c 加 `s_mcan0_msg_buf[MCAN_MSG_BUF_SIZE_IN_WORDS](640字=2560B) ATTR_PLACE_AT(".ahb_sram")`，
  can_app_init 里 mcan_init 前 `mcan_set_msg_buf_attr(MCAN0, {base, 2560})`；注册失败时 g_can_err=2 区分。
- SES 链接脚本 flash_xip.icf 含 .ahb_sram 段（→AHB_SRAM region），无需改工程。
- 参考：官方 samples/drivers/mcan/src/mcan_app_common.c（s_can_info[].ram_base/ram_size 同样做法）。
- **HPM5361 上 MCAN 移植要点（双重坑）：①时钟源 PLL1 必须初始化；②Message RAM 必须注册。两者缺一 mcan_init 都失败。**

### 第一轮（08:38 诊断）
- 现象：USB-CAN Tool（USBCAN-II，500k）收不到 0x201/0x202；J-Scope 看 `g_can_tx_cnt` 在涨但 `g_can_err` 恒为 1。
- 判读：`send_frame()` 只把帧塞进 TX FIFO 就计数，控制器没起来照样涨 → tx_cnt 涨不代表总线有帧；**g_can_err=1 才是铁证**（mcan_init 失败）。
- 根因：E249 移植的 `boards/hpm5300evk/clock.c` 里 `init_board_clock_source()` 只初始化了 PLL0(960MHz)，而 `init_can0_clock()` 用 `clk_src_pll1_clk0`（÷10）作 CAN0 功能时钟源 → PLL1 没跑，mcan_init 失败。
- 修复：在 `init_board_clock_source()` 补 PLL1 初始化（XTAL 参考，400MHz，clk0 postdiv div_1p0）→ CAN0 = 400/10 = 40MHz，500kbps 标准 80tq。
- 语法检查（hpm-sdk-ses-syntax-check，复用 hpm5300evk_flash_xip_debug SES 配置）：error 0 / warning 0。
- 待办：重新编译烧录后，J-Scope 确认 g_can_err=0、CAN 盒出现 0x201(100ms)/0x202(500ms)；再发 0x100 验证回 0x1F0。
- 经验：USB-CAN Tool 帧率T 只代表"软件已提交发送"；单节点无 ACK 时发送会重试。判链路通不通要看对端帧率R。
