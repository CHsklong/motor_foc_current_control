## 11:00 解决"第一次烧录能转、之后重新上电都不转"——新增运行监护 app_keeper

用户反馈：git reset 后重新烧录那一次电机能转，之后无论重新上电几次都完全不转。
（今天的上电时序修复确认全部保留：POWER_UP_SETTLE_MS、PWM 故障锁存清除、
pwm_init 前置、MT6835 自检重试、编码器抗撕裂、ADC 零点校准重试。）

### 根因思路：闭环里有三处"单向锁死"，触发窗口正好在上电爬升期
1. **PWM 硬件故障锁存**：pwm_init() 配的是 `fault_recover_at_rising_edge=false`
   （禁止硬件自动恢复、需软件清标志）。外部过流比较器(TL331,PA10,低有效)在上电
   毛刺期拉一下低 → 六路输出被永久钉死为 0。此时 CPU/20kHz 中断/心跳全正常，
   只有 PWM SR.FAULT 位能看出来。原代码只在启动阶段清一次，之后再 latch 无人管。
2. **MCL detect 的 disable_output 回调**：判出任何故障（含上电误判）就关断输出，无恢复路径。
3. **母线电压只读一次**：motor_init() 里 `read_vbus()` 发生在 pwm_init() 之前，
   const_vbus 之后不再刷新；冷上电在模拟前端未稳时读到偏低值 → 电压限幅偏小 → 出力不足。
三者都能解释"调试器下载后必转、冷上电不转"：下载时板子早已上电，这些瞬态窗口已过。

### 改动
- 新增 `src/app/app_keeper.c/.h`（CMakeLists 加一行）：1ms 调一次的运行监护
  - ① PWM latch → pwm_fault_clear()；② 输出被关 → enable_all_pwm_output()；
    ③ loop.status==fail → loop_disable/enable 软重启；④ 上电 1s 后复核并修正 vbus
  - 启动延时 1s + 动作冷却 500ms + 总动作上限 8 次
  - **安全边界**：只在 g_fault_src==0 时自愈；涉及 bit0(采样/过流)/bit2(驱动) 永不自愈；
    仅 bit1(环路)/bit3(编码器) 且在上电 3s 窗口内允许一次软恢复（这三类不会烧功率级）
- `dbg_probe.h/.c` 新增探针：g_keeper_fault_clr / out_rec / loop_rec / vbus_upd /
  blocked / last_cause、g_vbus_now
- `drv_pwm.c`：PWMv2 分支的 disable 是 force output_1(高)、与 v1 的 output_0(低)相反，
  加注释警示（HPM5300 走 v1，nm 确认无 pwmv2 符号）

ninja 通过，FLASH 109016 B；nm 确认 app_keeper_update 与全部 g_keeper_* 链入，
emProject 含 app_keeper.c，debug 连接仍为 J-Link。待用户 SES Build+Download 验证。

### 判读清单（给用户）
g_keeper_blocked≠0 → 真实故障拒绝自愈，看 g_fault_src 位图；
g_keeper_fault_clr>0 → 锁存已自愈；out_rec>0 → 输出恢复；loop_rec>0 → 环重启；
vbus_upd>0 → 母线修正，对比 g_boot_vbus 与 g_vbus_now。

## 13:20 定位"g_heart_isr 递增但 g_heart_main 不变"

用户观察：20kHz 中断心跳在涨，主循环心跳一动不动。
已排除（静态分析）：
- 不是中断风暴：adc_isr_enable() 只使能 TRIG_COMPLETE 一种事件，ISR 里也清了它。
- 不是主上下文/中断抢 SPI：ISR 里只在 g_encoder_isr_enable=1 时调 hpm_mcl_encoder_process()（SPI），
  而该标志初值 0，要到 step13 之后的 SKIP_ALIGN 分支才置 1 —— step11/12 的 mt6835 读不受影响
  （但 step13 之后 ISR 每拍都要读一次编码器，这是中断耗时的大头候选）。
- 不是 board_delay_ms 死等：hpm5300evk/board.c 里 board_delay_ms → clock_cpu_delay_ms，
  基于 CPU 周期计数，不依赖任何定时器中断，timer_init() 不会和它冲突。

剩余两大可能，已加探针区分：
1. **被 20kHz 中断饿死**：ISR 单拍超时（预算 50us）→ CPU 几乎全在中断 → main 得不到执行。
   最可能的变慢源是编码器 SPI 从"单次连读 5us"退化成"三次单字节 25us"（看 g_seq3_ok 是否 0）。
2. **main 真卡在某个初始化调用**：看 g_boot_step 停在第几号（13 之后到 17 之间没有打点，
   中间是 set_initial_theta → loop_disable → delay20 → loop_enable → 位置给定）。

新增探针：g_isr_cycles_last / g_isr_cycles_max / g_isr_over_cnt / g_isr_us_max / g_isr_us_last。
实现：isr_adc 入口 hpm_csr_get_core_cycle() 计时，出口 isr_timed_end() 统计，
超预算（mcu_clock_tick/PWM_FREQUENCY）计 g_isr_over_cnt；us 换算在 app_monitor_update() 里做。
顺带：app_monitor 里被注释掉的 g_vbus 改为读 motor0.cfg.mcl.physical.motor.vbus（const_vbus 同源）。

ninja 通过，FLASH 108792 B；nm 确认 5 个 g_isr_* 符号链入。已提交 c3e54cf。

## 13:50 分段计时版验证结果：main 恢复运行，但确认了"ISR 偶发超预算"的根因

新固件读数：g_heart_main≈28000+ 持续递增、g_main_step 在 1~5 间正常跳 → main 活了。
同时拿到关键数据（max-since-boot）：**g_enc_us_max=65~85us、g_loop_us_max=122us、
g_isr_us_max=139~159us** —— 编码器读取段单次竟到 85us（正常突发读应 ~10us 级），
环路段单次到 122us，都远超 50us 预算；只是这次没有持续，main 没被饿死。

结论：冻死 = 20kHz ISR 进入"持续超预算状态"（最可疑是编码器段 SPI 读退化），
把 main 完全饿死；它有随机性（上电状态依赖），这轮没触发所以"看起来好了"。
与用户"冷上电时好时坏"的总体现象吻合。问题未根治，属于概率性风险。

待办（后续硬化）：max 改窗口化（周期清零）区分启动尖峰与运行期尖峰；
压 ISR 峰值（编码器单次突发读、必要时查 SPI 时钟配置）。
